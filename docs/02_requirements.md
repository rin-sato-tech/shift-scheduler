## 2. 本書の目的

本書は、シフト自動作成デモが満たすべき機能要件、業務ルール、非機能要件、制約および受入条件を定義する。

プロジェクトの背景、想定利用者、対象業務の全体像は`01_overview.md`に記載する。

システム構成とモジュール設計は`03_system_design.md`、データベースとPythonモデルの定義は`04_data_definition.md`、OR-Toolsを用いた制約モデルの詳細は`05_schedule_constraints.md`に記載する。

## 3. システムの目的

本システムは、従業員情報、希望休、必要人数をもとに、1か月分の勤務シフトを自動生成するWebアプリケーションである。

次の目的を達成する。

- 月間シフト作成に必要な情報を一元管理する
- 希望休、勤務可否、必要人数などの条件を満たすシフトを自動生成する
- 入力不足や生成後の制約違反を検出し、利用者へ示す
- 自動生成後の手動調整と再検証を可能にする
- 日付別・従業員別の両方からシフトを確認できるようにする
- 確定したシフトを管理用・個人配布用の形式で出力する

---

## 4. 想定利用者

### 4.1 シフト作成担当者

本システムの主な利用者は、小規模事業所において月間シフトを作成・管理する担当者とする。

利用者は、次の業務を行う。

- 従業員、希望休、必要人数などの入力情報を管理する
- 入力内容を検証し、月間シフトを自動生成する
- 日付別・従業員別の表で生成結果を確認する
- 必要に応じて配置を手動変更し、再検証する
- 確定したシフトと集計データをCSV出力する

### 4.2 対象外の利用者

現在のバージョンでは、次の利用形態を対象外とする。

- 従業員本人による希望休の直接入力
- 複数利用者による同時編集
- 閲覧専用アカウント
- 複数店舗の一元管理

認証および権限管理は実装しない。

個人用シフトカレンダーは、シフト作成担当者が出力して従業員へ配布する。

## 5. 業務前提

本システムでは、次の業務条件を前提とする。

| 項目         | 前提                          |
| ------------ | ----------------------------- |
| 対象組織     | 単一店舗または単一部署        |
| 従業員数     | 数名から数十名程度            |
| 作成期間     | 1か月単位                     |
| シフト区分   | 早番・遅番                    |
| 1日の配置    | 1人につき最大1シフト          |
| 希望休       | 日単位                        |
| 週の区切り   | ISO週に基づく月曜日から日曜日 |
| 週間勤務日数 | 最大5日                       |
| 連続勤務日数 | 最大5日                       |
| 契約勤務日数 | 必須一致ではなく最適化目標    |
| 連続勤務判定 | 対象月内のみ                  |
| データ保存   | SQLite                        |
| 利用環境     | ローカル環境                  |

必要人数と必要責任者数は、固定値ではなく日付・シフトごとに設定する。

## 7. 機能要件

### 7.1 FR-01 従業員管理

システムは、シフト作成に必要な従業員情報を登録・編集できること。

#### 管理項目

- 従業員ID
- 氏名
- 責任者区分
- 月間契約勤務日数
- 早番・遅番の勤務可否
- 有効状態

#### 入力条件

- 従業員IDと氏名を必須とする
- 従業員IDは重複不可とし、登録後は変更しない
- 契約勤務日数は0以上31以下とする
- 早番または遅番の少なくとも一方を勤務可能とする
- 無効な従業員は新しいシフト生成の対象に含めない
- 無効化しても既存の希望休やシフトは削除しない

---

### 7.2 FR-02 希望休管理

システムは、対象月と従業員を指定し、月間カレンダーから希望休を登録・削除できること。

#### 登録

- 対象月内の日付を複数選択し、一括登録できること
- 選択した日付を再度クリックして選択解除できること
- 登録済み日付をカレンダー上で識別できること
- 同一従業員・同一日付の重複登録を禁止すること
- 無効な従業員への新規登録を禁止すること

#### 確認

対象月の希望休を一覧表示し、従業員で絞り込めること。

一覧には、日付、曜日、従業員ID、氏名、有効状態を表示する。

#### 削除

- 従業員を選択し、登録済み日付をカレンダー表示できること
- 複数の希望休を選択して一括削除できること
- 未登録の日付を削除対象として選択できないこと

選択状態は対象月・従業員・処理種別ごとに分離し、登録または削除の完了後に解除する。

---

### 7.3 FR-03 必要人数設定

システムは、対象月の日付・シフトごとに次の値を設定できること。

- 必要人数
- 必要責任者数

対象シフトは早番と遅番の2種類とする。

#### 入力条件

- 必要人数と必要責任者数は0以上とする
- 必要責任者数は必要人数以下とする
- 対象月内の日付のみ設定できること
- 同一日付・同一シフトの設定は1件とする

対象月の全日・全シフトへの一括設定と、日付・シフト単位の個別調整を可能にする。

---

### 7.4 FR-04 入力データ事前検証

システムは、シフト生成前に次の項目を検証できること。

| 分類       | 主な検証内容                         |
| ---------- | ------------------------------------ |
| 従業員     | 有効従業員・責任者の存在             |
| 必要人数   | 全日・全シフトの設定、値の妥当性     |
| 勤務可能者 | 希望休と勤務可否を考慮した人数の充足 |
| 配置可能量 | 週5日上限を考慮した最大配置数        |
| 契約日数   | 必要勤務枠との差や対象月日数超過     |

検証結果は`error`と`warning`に分類する。

`error`が1件以上ある場合はシフト生成を実行できないこと。

---

### 7.5 FR-05 シフト自動生成

システムは、OR-Toolsを使用して対象月のシフトを自動生成できること。

#### 必ず満たす条件

- 1人につき1日最大1シフト
- 希望休への配置禁止
- 勤務可能なシフトへのみ配置
- 必要人数の充足
- 必要責任者数の充足
- 1週間の勤務日数を5日以内とする
- 連続勤務日数を5日以内とする

#### 制約と最適化

- 生成結果は8章のハード制約を満たすこと
- 10章のソフト制約に基づき、契約勤務日数との差を最小化すること
- Solverに実行時間の上限を設定できること
- 通常のデモ条件では30秒以内に結果を返すことを目標とする

既存シフトがある場合は、利用者の確認後に新しい生成結果へ置き換える。

生成結果とSolverステータスを表示し、生成に成功した場合はデータベースへ保存する。

#### 保存条件

- `OPTIMAL`または`FEASIBLE`の場合のみ保存する
- 対象月の既存シフトは、利用者の確認後に生成結果へ置き換える
- 自動生成された配置は`is_manual=False`とする
- シフト全体の置換はトランザクション内で行う

---

### 7.6 FR-06 シフト表示・集計

システムは、保存済みシフトを複数の形式で確認できること。

#### 日付別月間シフト表

日付、曜日、早番配置者、遅番配置者を表示する。

#### 従業員別月間シフト表

- 行を従業員、列を対象月の日付とする
- 各セルに`早`、`遅`、`休`のいずれかを表示する
- 手動変更された配置には`※`を付ける
- 早番、遅番、休みを背景色と文字の両方で識別できるようにする

日付別表と従業員別表はタブで切り替えられること。

#### 配置明細

日付、曜日、シフト、従業員、責任者区分、手動変更区分を1配置1行で表示する。

#### 従業員別勤務集計

従業員ごとに、契約勤務日数、割当勤務日数、差、早番・遅番回数、最大連続勤務日数、責任者配置回数を表示する。

---

### 7.7 FR-07 制約検証

システムは、保存済みシフトおよび手動変更案について、次の制約を検証できること。

- 1日1シフト
- 希望休
- 勤務可能シフト
- 必要人数
- 必要責任者数
- 週間勤務日数
- 連続勤務日数
- 契約勤務日数との差

検証結果には、重大度、ルールID、対象日、シフト、従業員およびメッセージを含める。

重大度は次の2種類とする。

- `error`：確定前に修正が必要
- `warning`：確認を推奨

---

### 7.8 FR-08 シフト手動変更

システムは、保存済みシフトを画面上で変更できること。

変更後の勤務区分は、早番、遅番、休みから選択する。

#### 必要な操作

- 日付と従業員を指定して勤務区分を変更する
- 変更内容を一時的な編集案として保持する
- 変更前後の差分を確認する
- 編集案全体を再検証する
- 編集案を保存または破棄する

`error`が残っている場合は保存できないこと。

保存時は対象月のシフト全体をトランザクションで置き換える。

---

### 7.9 FR-09 CSV出力

システムは、保存済みシフトを次の5種類のCSVとして出力できること。

| 出力                   | 内容                             |
| ---------------------- | -------------------------------- |
| 日付別月間シフト表     | 日付ごとの早番・遅番配置者       |
| 従業員別月間シフト表   | 従業員ごとの日別勤務区分         |
| 個人用シフトカレンダー | 選択した従業員の月間カレンダー   |
| 配置明細               | 1配置1行の詳細データ             |
| 従業員別勤務集計       | 勤務日数、シフト回数、連続勤務等 |

#### 共通条件

- 保存済みシフトが存在する場合のみ出力できること
- 出力前に画面上で内容を確認できること
- UTF-8 BOM付きCSVとすること
- 対象月をファイル名に含めること
- 手動変更された配置には`※`または手動変更区分を付けること

個人用シフトカレンダーは月曜日始まりとし、対象月外のセルを空欄にする。

CSVには背景色、罫線、列幅などの書式情報を含めない。

---

### 7.10 FR-10 データ管理

システムは、起動時に必要なSQLiteテーブルを自動作成できること。

データアクセスはRepository層へ集約し、画面からSQLを直接実行しない。

複数レコードをまとめて更新する処理は、必要に応じてトランザクションを使用する。

補助スクリプトにより、次の整合性を確認できること。

- 必要なテーブルの存在
- 主キー・一意制約
- 孤立参照の有無
- 月間シフトの基本的な整合性

---

### 7.11 FR-11 DB初期化

システムは、アプリ起動時および各ページの直接表示時にDBを初期化できること。

初期化処理は、存在しないテーブルだけを作成し、既存データを削除しないこと。

---

### 7.12 FR-12 DB整合性確認

システムは、補助スクリプトによって次の整合性を確認できること。

- 外部キー違反
- 同一従業員の同日重複配置
- 不正なシフト区分
- 必要なテーブルの存在

整合性違反がある場合は、終了コード1を返すこと。

---

## 8. ハード制約

ハード制約は、シフト生成時および手動変更後の保存時に必ず満たす条件とする。

| 制約ID | 制約名             | 内容                                             |
| ------ | ------------------ | ------------------------------------------------ |
| HC-01  | 1日1シフト制約     | 1人は同じ日に複数シフトへ配置できない            |
| HC-02  | 希望休制約         | 希望休の日には配置できない                       |
| HC-03  | 勤務可能シフト制約 | 勤務不可のシフトには配置できない                 |
| HC-04  | 必要人数制約       | 日付・シフトごとの配置人数を必要人数と一致させる |
| HC-05  | 責任者配置制約     | 日付・シフトごとの責任者数を必要数以上とする     |
| HC-06  | 週間勤務日数制約   | 月曜日から日曜日までの勤務日数を最大5日とする    |
| HC-07  | 連続勤務制約       | 6日以上連続して勤務させない                      |
| HC-08  | 有効従業員制約     | 無効な従業員を新しいシフトへ配置しない           |

### 8.1 月境界

週間勤務日数と連続勤務日数は、現在のバージョンでは対象月内のデータだけを用いて判定する。

前月末および翌月初の勤務は考慮しない。

## 9. 警告基準

警告が存在してもシフトを保存できるが、利用者による確認を必要とする。

| 警告ID | 内容                                          |
| ------ | --------------------------------------------- |
| WR-01  | 契約勤務日数との差の絶対値が3日以上           |
| WR-02  | 両シフト勤務可能者の早番・遅番回数差が5回以上 |
| WR-03  | 責任者間の配置回数差が5回以上                 |
| WR-04  | 必要勤務枠と契約勤務日数合計が一致しない      |

警告値は業務ルールとして固定しており、現在は画面から変更できない。

---

## 10. ソフト制約・最適化対象

ソフト制約は、ハード制約を満たしたうえで可能な限り改善する条件とする。

| 制約ID | 制約名           | 内容                                 | 現在の扱い |
| ------ | ---------------- | ------------------------------------ | ---------- |
| SC-01  | 契約勤務日数近似 | 割当日数を契約勤務日数へ近づける     | 最適化     |
| SC-02  | 最大乖離抑制     | 一部従業員への不足・超過集中を抑える | 最適化     |
| SC-03  | シフト偏り抑制   | 早番または遅番への偏りを抑える       | 集計・警告 |
| SC-04  | 責任者偏り抑制   | 責任者配置の集中を抑える             | 集計・警告 |

現在の目的関数では、契約勤務日数との差を主な最適化対象とする。

早番・遅番の偏りと責任者配置の偏りは、生成結果の集計および警告として扱う。

---

## 11. エラー定義

エラーが存在するシフトは保存できない。

| エラーID | 内容                                      |
| -------- | ----------------------------------------- |
| ER-01    | 必要人数を満たしていない                  |
| ER-02    | 必要な責任者が配置されていない            |
| ER-03    | 希望休の日に配置されている                |
| ER-04    | 同一人物が1日に複数シフトへ配置されている |
| ER-05    | 1週間に6日以上勤務している                |
| ER-06    | 6日以上連続勤務している                   |
| ER-07    | 勤務不可シフトに配置されている            |
| ER-08    | 無効な従業員が配置されている              |
| ER-09    | 不明な従業員IDが配置に含まれている        |
| ER-10    | 不正なシフト区分が含まれている            |

エラーIDと内部の検証ルールIDは、実装上の都合により異なる場合がある。

## 12. 非機能要件

### 12.1 操作性

- 画面の順序に沿って操作できること
- トップ画面に基本的な操作順を表示すること
- 対象年と対象月を共通形式で選択できること
- 入力エラーの理由を具体的に表示すること
- 成功・警告・エラーを区別して表示すること
- データがない場合に適切な案内を表示すること
- 保存後の再描画でも結果メッセージを確認できること
- 希望休を月間カレンダーから複数選択できること
- 月間シフトを日付別・従業員別に切り替えて確認できること

### 12.2 性能

- 数名から数十名、1か月、2シフトの条件で利用できること
- Solverに実行時間の上限を設定できること
- 通常のデモ条件では30秒以内の生成を目標とすること
- 大量データを前提とした性能保証は行わない

### 12.3 信頼性

- 外部キー制約を有効にすること
- 重複登録をDB制約でも防止すること
- 月間シフトの置換をトランザクション内で行うこと
- 保存途中の失敗時にロールバックされること
- 生成成功時のみシフトを保存すること
- 手動変更後は再検証を行うこと

### 12.4 保守性

- 画面、業務処理、DB処理、検証処理を分離すること
- SQLを画面コードへ直接記述しないこと
- DBレコードをPythonモデルへ変換すること
- 共通UI処理を再利用できること
- 表示用DataFrame変換を画面から分離すること
- 型ヒントを使用すること
- 主要処理に自動テストを用意すること

### 12.5 可搬性

- Pythonが利用できる環境で実行できること
- macOS、Windows、Linuxでのローカル実行を想定する
- DBパスはプロジェクトルートを基準に決定すること
- Excelで日本語が文字化けしにくいUTF-8 BOM付きCSVを出力すること

### 12.6 セキュリティ

現在はローカルデモであるため、次を前提とする。

- インターネットへ公開しない
- 信頼できる利用者が使用する
- 実在する個人の機密情報を保存しない
- 認証・権限管理を必要とする本番用途には使用しない

### 12.7 テスト

- pytestで自動テストを実行できること
- テスト用DBをアプリ用DBから分離すること
- 正常系と異常系を確認すること
- Repository、サービス、検証、生成、手動変更、出力を確認すること
- 一連の操作を確認する統合テストを用意すること
- DB整合性を補助スクリプトで確認できること

## 13. データ要件

- 日付は`YYYY-MM-DD`形式でDBへ保存する
- 対象月は`YYYY-MM`形式で扱う
- 日時はタイムゾーン付きISO 8601形式で保存する
- 真偽値はSQLite上で`0`または`1`として保存する
- シフト区分は`early`または`late`とする
- 同一従業員・同一日のシフトは1件までとする
- 従業員は物理削除せず有効状態で管理する
- 希望休は物理削除を許可する
- 対象月のシフトは一括置換できること

詳細は`04_data_definition.md`に記載する。

## 14. 対象外

現在のバージョンでは、次を対象外とする。

- 従業員本人による希望休入力
- ログイン・認証
- 利用者ごとの権限管理
- 複数店舗・複数部署
- 複数利用者による同時編集
- 早番・遅番以外のシフト種別
- 時刻単位の勤務管理
- 休憩時間管理
- 週40時間の実労働時間計算
- 残業時間の計算
- 勤務間インターバル
- 法定休日の厳密な管理
- 有給休暇残数管理
- 給与計算
- 前月末を含む連続勤務判定
- 生成履歴の一覧・詳細画面
- Excel形式での直接出力
- PDF形式での帳票出力
- メールやチャットによる通知
- 外部システム連携
- クラウド上での本番運用
- 監査ログ
- バックアップ・復元画面

## 15. 受入条件

### 15.1 従業員管理

- 入力条件を満たす従業員を登録・編集できる
- 重複した従業員IDを拒否できる
- 勤務可能シフトがない状態を拒否できる
- 従業員を無効化・再有効化できる

### 15.2 希望休

- カレンダーから複数日を選択して一括登録できる
- 選択した日付を再度クリックして解除できる
- 登録済み希望休をカレンダー上で識別できる
- 重複希望休と対象月外の日付を拒否できる
- 登録済み希望休を複数選択して一括削除できる
- 未登録の日付を削除対象として選択できない

### 15.3 必要人数

- 月全体へ一括設定できる
- 日付・シフト単位で調整できる
- 必要責任者数が必要人数を超える値を拒否できる
- 保存後に同じ内容を再取得できる

### 15.4 シフト生成

- 事前検証結果を表示できる
- エラーがある場合は生成を開始しない
- 実行可能な条件ではシフトを生成できる
- 希望休へ配置しない
- 勤務不可シフトへ配置しない
- 必要人数と必要責任者数を満たす
- 週5日上限と最大5連勤を満たす
- 生成結果をDBへ保存できる
- 同じ月を再生成できる

### 15.5 シフト表示・集計

- 日付別月間シフト表を表示できる
- 従業員別月間シフト表を表示できる
- 両方の表をタブで切り替えられる
- 従業員別表に早番・遅番・休みを正しく表示できる
- 勤務区分を文字と背景色で識別できる
- 配置明細と従業員別勤務集計を表示できる

### 15.6 手動変更

- 早番・遅番・休みへ変更できる
- 複数変更を編集案として保持できる
- 変更前後の差分を確認できる
- 制約違反を再検証できる
- エラーがある編集案を保存できない
- 正常な編集案を保存できる
- 編集案を破棄できる

### 15.7 CSV出力

- 日付別月間シフト表を出力できる
- 従業員別月間シフト表を出力できる
- 選択した従業員の個人用カレンダーを出力できる
- 配置明細を出力できる
- 従業員別勤務集計を出力できる
- Excelで日本語が文字化けしない
- 手動変更の情報を確認できる
- 個人用カレンダーの日付が正しい曜日位置に配置される

### 15.8 品質

- 全自動テストが成功する
- DB整合性確認が成功する
- 主要な手動テストが完了する
- 保存失敗時のロールバックを確認できる
- 既知の未対応事項が文書化されている
